# Plano 0001 — Corpos d'água (`water_body`, PostGIS) + seed de rios/águas do RS via OSM

- **Status:** Implementado
- **Data:** 2026-06-14
- **Relacionado:** [ADR-0001](../adr/0001-pontos-de-pesca-postgis.md), [Spec 0001 (registro de pesca)](../specs/0001-registro-de-pesca.md), [CONTEXT](../CONTEXT.md)

> **Nota de nomenclatura:** este plano foi escrito originalmente como
> `fishing_spot`, mas o conceito foi renomeado para **`water_body`** (camada de referência: rios/lagos
> do seed). A "pesca" do usuário é o **`catch_record`** ([Spec 0001](../specs/0001-registro-de-pesca.md)),
> que referencia este `water_body`. Os identificadores abaixo já usam o nome novo.

## Objetivo

Criar a entidade de **corpo d'água** (`water_body`) no backend (geometria real,
PostGIS), expor um endpoint consumido pelo mapa do app, e **popular
automaticamente** os corpos d'água do Rio Grande do Sul a partir do OpenStreetMap.
Esta é a **camada de referência** sobre a qual os registros de pesca se apoiam.

**Decisões já tomadas:**
- Modelagem: **geometria real (PostGIS)**.
- Abrangência do seed: **massas d'água nomeadas + rios principais nomeados**
  (`natural=water` + `waterway=river`, ambos com `name`).

## Diagnóstico (situação atual)

- **Backend:** não existe entidade geográfica. `Fish` é só catálogo de espécies
  (sem lat/lon). Nenhum controller de "spot/local".
- **Front:** `app/lib/screens/map_screen.dart` tem 3 pontos *hardcoded*
  (`static const List<FishingSpot>` — classe local do app). O mapa **não chama o backend**.
- **Banco:** PostgreSQL (`docker-compose.yml`, imagem `postgres:16`).

## ⚠️ Pré-requisitos / armadilhas

1. **Numeração Flyway:** a maior migration aplicada hoje é `V4__seed_fish_rs.sql`
   (seed de espécies). A nova migration desta feature será **`V5`**. *(O antigo
   conflito de duas `V2` já foi resolvido no commit `23dc56e` — só existe
   `V2__create_users.sql`.)*
2. **`ddl-auto=validate`:** schema da migration precisa bater exatamente com a
   entidade JPA — atenção ao mapeamento do tipo `geometry`.

## Etapas

### 1. Infra: habilitar PostGIS
- `backend/docker-compose.yml` (único compose do repo): trocar
  `image: postgres:16` → `image: postgis/postgis:16-3.4` (drop-in; volume
  `postgres_data` é preservado).
- Testes: trocar a imagem do `testcontainers-postgresql` para PostGIS.
- A extensão é criada via migration (etapa 3).

### 2. Dependências (`backend/build.gradle`)
```gradle
implementation 'org.hibernate.orm:hibernate-spatial'   // versão gerenciada pelo BOM
implementation 'org.locationtech.jts:jts-core:1.20.0'
```
O dialeto Postgres do Hibernate 6 já suporta espacial — não trocar `hibernate.dialect`.

### 3. Migration `V5__enable_postgis_and_water_bodies.sql`
```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE water_body (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    water_type  VARCHAR(50)  NOT NULL,              -- RIVER, LAKE, LAGOON, RESERVOIR, POND
    geom        geometry(Geometry, 4326) NOT NULL,  -- SRID 4326 (WGS84)
    osm_id      BIGINT,                             -- rastreabilidade p/ re-importar
    source      VARCHAR(50) NOT NULL DEFAULT 'OSM',
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at  TIMESTAMP WITH TIME ZONE
);

CREATE INDEX idx_water_body_geom ON water_body USING GIST (geom);
CREATE UNIQUE INDEX uk_water_body_osm ON water_body (osm_id) WHERE osm_id IS NOT NULL;
```
- `geometry(Geometry, 4326)` genérico: rios = `LineString`/`MultiLineString`,
  massas = `Polygon`/`MultiPolygon`.
- Índice **GIST** torna o filtro por bounding box rápido.

### 4. Backend (espelhar padrão de `Fish`)
- `entity/WaterType.java` — enum `RIVER, LAKE, LAGOON, RESERVOIR, POND`.
- `entity/WaterBody.java` — estilo de `Fish.java` (`@Data/@Builder`, auditoria),
  campo `org.locationtech.jts.geom.Geometry geom` com
  `@Column(columnDefinition = "geometry(Geometry,4326)")`.
- `repository/WaterBodyRepository.java` — consulta por viewport:
  ```java
  @Query(value = "SELECT * FROM water_body WHERE ST_Intersects(geom, ST_MakeEnvelope(:minLon,:minLat,:maxLon,:maxLat,4326))", nativeQuery = true)
  List<WaterBody> findInBbox(double minLon, double minLat, double maxLon, double maxLat);
  ```
- `dto/WaterBodyResponseDTO.java` — serializar `geom` como **GeoJSON**
  (via `ST_AsGeoJSON` na query ou `jackson-datatype-jts`).
- `controller/WaterBodyController.java` —
  `GET /api/water-bodies?bbox=minLon,minLat,maxLon,maxLat` (fallback p/ bbox do RS).
- `security/SecurityConfig.java` — `GET /api/water-bodies/**` segue a regra
  atual (`GET /api/**` → `authenticated()`, `SecurityConfig:60`); ou seja, exige
  usuário logado, como `/api/fish`. **Decidido:** manter autenticado (sem regra
  nova); o mapa carrega após login.

### 5. Seed — importador OSM via Overpass
**Abordagem:** importador rodável sob demanda (não SQL gigante commitado —
geometria de milhares de feições incharia o repositório).

Implementar como `ApplicationRunner` ativado por flag
(`--app.seed.water-bodies=true`) que:
1. POST para `https://overpass-api.de/api/interpreter` com:
   ```overpassql
   [out:json][timeout:180];
   area["ISO3166-2"="BR-RS"]->.rs;
   (
     way["natural"="water"]["name"](area.rs);
     relation["natural"="water"]["name"](area.rs);
     way["waterway"="river"]["name"](area.rs);
     relation["waterway"="river"]["name"](area.rs);
   );
   out geom;
   ```
2. Converte para geometria JTS (ways → `LineString`/`Polygon`; relations →
   `Multi*`), mapeia `name`, deriva `water_type` das tags.
3. **Upsert por `osm_id`** (idempotente).

**Notas operacionais:**
- Overpass é compartilhada e tem limite de uso → rodar uma vez e persistir.
- Filtro `["name"]` mantém o volume em "milhares" e corta riachos anônimos.
- **Plano B (fonte oficial, sem limite de API):** shapefile de hidrografia do
  **IBGE (BC250)** ou **ANA (BHO)** importado com `ogr2ogr -f PostgreSQL`.
