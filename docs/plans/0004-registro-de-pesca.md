- **Status:** Proposto

## Objetivo

Implementar a feature da [Spec 0001](../specs/0001-registro-de-pesca.md): o usuário
registra uma pesca (espécie da seed + ponto no mapa + detalhes + fotos), o clima é
preenchido automaticamente, e a privacidade do local (ADR-0002) é garantida no
servidor. Inclui backend (entidades, endpoints, upload, clima) e o fluxo no app.

## Diagnóstico (situação atual)

- **Espécies (`fish`):** catálogo pronto e **semeado** (plano 0003, `V4__seed_fish_rs.sql`).
  `GET /api/fish` paginado, exige auth. → dependência **satisfeita**.
- **`water_body` (PostGIS):** **em implementação agora** (plano 0001 *Em
  andamento*). É **pré-requisito**: `catch_record.water_body_id` é FK NOT NULL e a
  geometria exige PostGIS habilitado. → esta feature começa quando o 0001 expuser
  `water_body` + PostGIS.
- **Auth/usuário:** JWT (resource-server). `authentication.getName()` = e-mail do
  usuário (subject do JWT); o padrão de resolver usuário por e-mail já existe
  (`MeController:30`, `MeService.getByEmail`). User → tabela `users`.
- **SecurityConfig (armadilha crítica):** as regras são **genéricas por método**
  (`SecurityConfig:63-66`): `POST/PUT/PATCH/DELETE /api/**` → **`hasRole("ADMIN")`**.
  Hoje **um usuário comum NÃO consegue** `POST /api/catches` nem deletar a própria
  pesca. → **precisa de matchers explícitos** para `/api/catches/**` antes das
  regras genéricas (ver [Segurança](#segurança--autorização)).
- **Upload de arquivos:** não há nada (nem `ResourceHandler`, nem dir de uploads,
  nem multipart). → construir do zero.
- **App:** tem `flutter_map ^7`, `latlong2`, `http`. **Falta `image_picker`**
  (fotos). `map_screen.dart` ainda usa pontos hardcoded (some com o plano 0001).
- **Conflito de `V2` (plano 0001):** **já resolvido** — existe só uma `V2`
  (`V2__create_users.sql`). Sem trava de banco limpo.
- **Stack:** Spring Boot **4.0.6**, Jackson **3** (`tools.jackson`), JPA
  auditoria (`@CreatedDate`), testes com Testcontainers (`postgres:16` — vira
  `postgis/postgis` no plano 0001).

## Modelo de dados

### Migration `V6__create_catch_records.sql` (rascunho)

> Depende da `V5` do plano 0001 (PostGIS habilitado + tabela `water_body`).

```sql
CREATE TABLE catch_record (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id             BIGINT NOT NULL REFERENCES users(id),
    water_body_id       BIGINT NOT NULL REFERENCES water_body(id),
    location            geometry(Point, 4326) NOT NULL,
    location_visibility VARCHAR(20)  NOT NULL,           -- EXACT | RIVER_ONLY
    species_id          BIGINT NOT NULL REFERENCES fish(id),
    weight_grams        INT,
    length_mm           INT,
    description         TEXT,
    fishing_method      VARCHAR(20)  NOT NULL,           -- ARREMESSO, FLY, ...
    purpose             VARCHAR(20)  NOT NULL,           -- SPORT | CONSUMPTION
    caught_at           TIMESTAMP WITH TIME ZONE NOT NULL,
    -- clima embutido (1:1, best-effort, todos nullable)
    weather_temperature_c     NUMERIC(4,1),
    weather_condition         VARCHAR(20),
    weather_wind_speed_kmh    NUMERIC(5,1),
    weather_wind_direction_deg INT,
    weather_humidity_pct      INT,
    weather_pressure_hpa      NUMERIC(6,1),
    weather_code              INT,                        -- WMO bruto
    weather_captured_at       TIMESTAMP WITH TIME ZONE,
    weather_source            VARCHAR(20),                -- default OPEN_METEO
    created_at          TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at          TIMESTAMP WITH TIME ZONE
);
CREATE INDEX idx_catch_location  ON catch_record USING GIST (location);
CREATE INDEX idx_catch_user      ON catch_record (user_id);
CREATE INDEX idx_catch_species   ON catch_record (species_id);

CREATE TABLE catch_photo (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    catch_record_id BIGINT NOT NULL REFERENCES catch_record(id) ON DELETE CASCADE,
    file_path       VARCHAR(512) NOT NULL,
    position        INT NOT NULL DEFAULT 0,
    created_at      TIMESTAMP WITH TIME ZONE NOT NULL
);
CREATE INDEX idx_catch_photo_record ON catch_photo (catch_record_id);
```

- `created_at` NOT NULL sem default — auditoria JPA preenche no `persist`
  (entidades aqui são salvas via JPA, não SQL bruto → ok).
- Deleção: `ON DELETE CASCADE` remove as linhas de `catch_photo`, **mas não os
  arquivos no disco** → o service apaga os arquivos (ver [Fotos](#fotos--upload)).

## Backend — camadas

### DTOs
- `CatchRequestDTO` (criação): `waterBodyId`, `location {lat, lon}`,
  `locationVisibility`, `speciesId`, `weightGrams?`, `lengthMm?`, `description?`,
  `fishingMethod`, `purpose`, `caughtAt`. Validação Bean Validation (`@NotNull`
  nos obrigatórios, faixas em peso/comprimento). **Reutilizado no `PUT`** (edição).
- `CatchResponseDTO`: dados + `species` (resumo do fish) + `weather` + `photos[]`
  + `waterBody` (resumo) + `location` **condicional** (privacidade).
- `LocationDTO {lat, lon}` na entrada; na saída a geometria vai como **GeoJSON**
  ou `{lat, lon}` — reutilizar a decisão de serialização de geometria do plano
  0001 (JTS + Jackson 3: `ST_AsGeoJSON` na query nativa **ou** serializer custom;
  `jackson-datatype-jts` é Jackson 2 e **não** serve aqui).

### Service — `CatchService`
- `create(dto, requesterEmail)`: resolve `User` por e-mail; valida FKs
  (`water_body`, `fish` existem); monta `Point` (JTS `GeometryFactory`, SRID 4326);
  busca clima (best-effort); persiste.
- `update(id, dto, requesterEmail)`: **só dono**; re-valida FKs; recalcula clima
  se `location`/`caught_at` mudarem (best-effort). Fotos são geridas pelos
  endpoints próprios (não no `update`).
- `findAll(filtros, requester)` / `findById(id, requester)` / `findMine(requester)`
  / `delete(id, requester)` (só dono → senão 403/404).
- **Privacidade centralizada:** um único `toDto(CatchRecord, requester)` decide
  expor ou não `location` (ver ADR-0002). Nenhum outro caminho serializa
  `CatchRecord` cru.

### Segurança / autorização
- **SecurityConfig:** adicionar matchers **antes** das regras genéricas
  (`SecurityConfig:63`):
  ```java
  .requestMatchers(HttpMethod.POST,   "/api/catches/**").authenticated()
  .requestMatchers(HttpMethod.DELETE, "/api/catches/**").authenticated()
  .requestMatchers(HttpMethod.PUT,    "/api/catches/**").authenticated()
  ```
  (As regras `…/api/**` → ADMIN continuam valendo para o resto.)
- **Ownership** (dono-only em delete/futuro update) é checado **no service**, não
  só pelo matcher — o matcher só garante "logado".
- Servir fotos: `/uploads/**` não cai em `/api/**`; matcher explícito
  **`authenticated()`** (decidido — imagens não são públicas anônimas).

### Privacidade (impl. do ADR-0002)
- `toDto(catch, requester)`:
  - dono **sempre** vê `location` exato.
  - não-dono + `RIVER_ONLY` → **omitir** `location`; expor só `waterBody`
    (nome + centroide/geometria).
  - não-dono + `EXACT` → `location` incluído.
- **Teste de autorização dedicado** garantindo que o JSON para não-dono em
  `RIVER_ONLY` **não contém** `location` (anti-regressão de vazamento).

## Clima — integração Open-Meteo
- Cliente HTTP (`WeatherClient`) por `lat/lon` + `caught_at`.
- **Escolha de endpoint por idade do registro:** `caught_at` recente → **forecast**
  (`api.open-meteo.com/v1/forecast` com `past_days`); histórico antigo → **archive**
  (`archive-api.open-meteo.com/v1/archive`, ERA5). Definir o corte (sugestão: ~5
  dias, limite prático do `past_days`/disponibilidade do archive).
- Mapear `weather_code` (WMO) → `WeatherCondition`.
- **Best-effort:** timeout curto + `try/catch`; falha → campos de clima ficam
  **nulos**, o registro é criado normalmente (requisito da spec).
- **Sync vs async (decidido): inline** com timeout curto no `POST`/`PUT`
  (simples, sem infra extra). Evolução futura: assíncrono se a latência incomodar.

## Fotos / upload
- Fluxo de 2 passos (spec): `POST /api/catches` cria o registro; depois
  `POST /api/catches/{id}/photos` (multipart) anexa fotos.
- **Armazenamento:** filesystem local, dir configurável `app.uploads.dir`
  (`.gitignore`, fora de `src/`). Banco guarda só `file_path` relativo.
- **Validação (limites definidos):** tipos `image/jpeg`, `image/png`, `image/webp`;
  **máx 8 MB por arquivo**; **máx 8 fotos por registro**. Nome do arquivo = **UUID**
  + extensão (anti-colisão e anti-*path-traversal*).
- **Servir:** `ResourceHandler`/endpoint estático mapeando `app.uploads.dir` →
  `/uploads/**`.
- **Deleção:** ao deletar o `catch_record`, o service apaga os arquivos do disco
  (o CASCADE só limpa as linhas).
- Config Spring: `spring.servlet.multipart.max-file-size=8MB` /
  `max-request-size` (≥ 8 MB × lote; ex.: 64 MB).

## Endpoints
| Método | Rota | Auth | Descrição |
|---|---|---|---|
| `POST` | `/api/catches` | logado | cria registro (clima automático) |
| `POST` | `/api/catches/{id}/photos` | dono | upload multipart de fotos |
| `PUT` | `/api/catches/{id}` | dono | edita registro (recalcula clima se local/data mudarem) |
| `DELETE` | `/api/catches/{id}/photos/{photoId}` | dono | remove uma foto (linha + arquivo) |
| `GET` | `/api/catches` | logado | lista (privacidade; filtros: `bbox`, `speciesId`; paginado) |
| `GET` | `/api/catches/{id}` | logado | detalhe (privacidade) |
| `GET` | `/api/catches/mine` | logado | registros do usuário logado |
| `DELETE` | `/api/catches/{id}` | dono | remove (apaga fotos do disco) |

- `GET /api/catches?bbox=...`: para `RIVER_ONLY` de terceiros, o marcador usa o
  **centroide do `water_body`** (não o `location`), inclusive no filtro espacial.

## App — fluxo de criação
- **Deps:** adicionar `image_picker` (fotos). `flutter_map`/`latlong2` já existem.
- `models/catch_record.dart`, `services/catch_service.dart` (molde do `FishService`,
  com mock em `mock_data.dart`).
- **Tela de criação** (multi-step ou form único): **selecionar o `water_body`** +
  **marcar o ponto exato** no mapa (decidido: o **usuário define ambos no app** —
  toca o corpo d'água e marca o `location`) → escolher visibilidade (exato/rio) →
  selecionar espécie (consome `/api/fish`, picker do plano 0003) →
  peso/comprimento/descrição → método + finalidade → fotos (`image_picker`) →
  salvar. `caught_at` via date picker (default agora). O app envia `waterBodyId` +
  `location {lat, lon}`.
- **Tela de edição:** reusa o form de criação pré-preenchido; envia `PUT
  /api/catches/{id}`; permite adicionar/remover fotos (endpoints próprios). Só o
  dono vê a ação de editar.
- **No mapa:** marcadores das pescas (sobre os `water_body` do plano 0001);
  `RIVER_ONLY` aparece no centroide do corpo d'água, sinalizado como aproximado.

## Critérios de aceite (da spec)
- [ ] Usuário cria registro marcando ponto no mapa + corpo d'água.
- [ ] Pode ocultar o ponto exato (público só o rio) — respeitado **no JSON**.
- [ ] Espécie selecionada da seed (FK obrigatória).
- [ ] Peso, comprimento, descrição, método e finalidade salvos.
- [ ] Fotos anexadas (1..N), servidas e apagadas junto com o registro.
- [ ] Clima preenchido automaticamente (ou nulo, sem quebrar, se a API falhar).
- [ ] Usuário comum consegue criar/editar/deletar a própria pesca (SecurityConfig ok).
- [ ] Dono edita o registro (`PUT`) pela tela de edição; terceiro recebe 403/404.

## Decisões fechadas (nesta iteração)

- **Seleção de local:** o **usuário define `water_body` + ponto exato no app**; o
  app envia `waterBodyId` + `location {lat, lon}`.
- **Clima:** **inline**, best-effort, no `POST`/`PUT`.
- **Fotos (`/uploads/**`):** acesso **`authenticated()`**.
- **Limites de upload:** jpeg/png/webp, **8 MB/arquivo**, **8 fotos/registro**.
- **Edição:** **há** `PUT /api/catches/{id}` (dono) **e tela de edição** no app;
  remoção de foto individual via `DELETE /api/catches/{id}/photos/{photoId}`.
